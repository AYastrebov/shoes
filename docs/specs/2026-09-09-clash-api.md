# Clash API

An HTTP surface compatible with the Clash RESTful API as mihomo and sing-box
serve it, so that the dashboards written against it -- yacd, metacubexd,
zashboard, and the dashboards embedded in Clash-family GUIs -- can observe and
drive a running shoes without shoes learning their config format.

Written 2026-09-09 against `mobile` at `0bc4dfa` (v0.4.1). The named-outbounds
spec ([docs/superpowers/specs/2026-08-26-named-outbounds-design.md](../superpowers/specs/2026-08-26-named-outbounds-design.md))
listed "the connection list" and "the Clash API" as two design problems it
was not solving; this is both of them, because the second is not usable
without the first.

## Problem

A shoes running on a VPS or a router has no window into itself. The
counters exist -- two process-wide byte totals, a live-connection count, and
a per-outbound table keyed by name -- and a bounded log ring exists behind
`control-logs`, but the only things that read any of it are the mobile FFI
and the desktop daemon's gRPC stream. A headless shoes is observed by tailing
a log file.

The Clash API is the one observability contract that the proxy ecosystem has
standardised on. Every general-purpose dashboard speaks it, and so does every
Clash-family GUI's embedded panel. Serving it means a shoes on a router gets a
connection table, a traffic graph and a proxy picker from software that
already exists, at the cost of matching a JSON shape.

Three things stand in the way, and they are engine gaps rather than HTTP
work:

**There is no connection table.** `crate::tun::traffic::active_connections`
is one integer. Nothing records a connection's source, destination, chosen
outbound, matching rule or per-connection bytes, and nothing can close one
from outside. `/connections` is the first thing a dashboard opens, and it is
the endpoint that makes the API useful rather than decorative.

**The process-wide traffic counters are zero in server mode.** They are
incremented at the TUN edge (`src/tun/traffic.rs`, called from
`src/tun/mod.rs:481` and the stack) and nowhere else. On a VPS there is no
TUN. A `/traffic` stream derived from them would draw a flat line under real
load, which the named-outbounds spec named as a pre-existing asymmetry and
left in place. This project cannot leave it.

**No group is selectable.** `ClientChainGroup` is round robin
(`src/client_proxy_chain.rs:811`) with no notion of a chosen member and no
runtime-mutable state. The second thing a dashboard user does is click a
proxy; that needs a new group semantic, and a place to persist the choice.

## Scope

Three slices, each shippable on its own and each behind the same feature.
Slice 1 is specified in full here. Slices 2 and 3 are specified to the level
of their contracts, so that slice 1 does not paint them into a corner.

1. **Surface and read side.** The listener, authentication, CORS, WebSocket
   streams, and every endpoint that maps onto state shoes already holds.
   Plus the connection table, source-address plumbing, the rule index, and
   the server-mode traffic fix, because without those the surface is not
   usable.
2. **Selection.** A `select` group mode whose chosen member is runtime
   mutable, `PUT /proxies/{group}`, persistence of the choice, and the
   `Rule / Global / Direct` mode switch.
3. **Latency.** `GET /proxies/{name}/delay`, delay history in `/proxies`.

In scope for the whole of it: a `src/clash_api/` module behind feature
`clash-api`; a `control-connections` feature holding the table; a
`clash_api:` block in shoes YAML; the CLI mounting the listener; changes to
`ValidatedConfigs`, `ConnectDecision`, `TcpClientSetupResult` and the two
forward paths that make the table populable.

## Who this serves

Two consumers, distinguished by what they do besides talk HTTP.

**Dashboards** -- yacd, metacubexd, zashboard, and the panels inside Clash
Verge Rev, FlClash, Hiddify and the like when pointed at an external
controller -- connect to an already running core and only speak the API.
They are the target, and both purposes the user named ("reuse existing
dashboards" and "drive shoes from a Clash-speaking UI") are served by the
API alone.

**Frontends acting as launchers** -- Clash Verge Rev spawning its core -- also
write a mihomo-format YAML and start the binary on it. Serving them means
reading Clash config: `proxies`, `proxy-groups`, `rules` in Clash syntax,
and `PUT /configs` to reload it. That is a translator, a different project,
and the user chose to keep shoes' own config. Nothing here depends on that
choice being reversed later, and nothing here makes it harder.

## Where it runs

**The CLI is the host.** The scenario is a server, a VPS, a router. The
listener is started by `src/main.rs` once, outside the reload loop, when the
loaded config carries a `clash_api:` block.

**Mobile is untouched by construction.** The whole of this is behind
`clash-api`, which is off by default and which neither `scripts/build-android.sh`
(`--features control-stats`) nor `scripts/build-apple.sh` enables. The
connection table is behind `control-connections`, which `clash-api` pulls in
and `desktop` does not. The one hot-path file every build compiles,
`src/outbound_counting_stream.rs`, gains an optional second counting target
under `#[cfg(feature = "control-connections")]`, so a build without the
feature has the same code it has today. This is verified rather than
asserted: [Testing](#testing) builds the mobile feature set and checks the
symbol table for the new modules.

**`shoesd` can mount it later.** The module takes the registries it reads
and a shutdown receiver; nothing in it knows about `main.rs`. When the
daemon wants it, `StartRequest` gains the same block and the daemon mounts
it on the service runtime, loopback only, secret mandatory. That is a later
change to the daemon contract and is not designed here beyond noting that
the module's interface allows it.

The feature graph in `Cargo.toml`:

```toml
control-connections = ["control-stats"]   # the per-connection table
clash-api = ["control-logs", "control-connections", "dep:serde_json"]
desktop = ["control-logs", "control-stats"]                  # unchanged
```

`serde_json` is already an optional dependency for the daemon and a dev
dependency; `clash-api` enables the same optional. hyper 1.x and
http-body-util are already unconditional dependencies (naiveproxy, hysteria2,
the TLS server handler). No new crate is required for slice 1.

## Compatibility target

mihomo's `hub/route` on the `Alpha` branch, as of 2026-09-09, is the
reference: it is what the dashboards are developed against, and sing-box
tracks it. The route table there, with what this design does about each
entry:

| mihomo route | Slice | Notes |
|---|---|---|
| `GET /` | 1 | `{"hello":"shoes"}` |
| `GET /version` | 1 | `{"version":"0.4.1","meta":true}`; `meta` is what dashboards test to enable the richer UI |
| `GET /traffic` | 1 | WebSocket or chunked stream, one `{"up":N,"down":N}` per second |
| `GET /memory` | 1 | WebSocket or chunked stream, one `{"inuse":N,"oslimit":0}` per second |
| `GET /logs` | 1 | WebSocket or chunked stream, `{"type":"info","payload":"..."}`; `?level=` filters |
| `GET /configs` | 1 | read only; the fields dashboards read, see below |
| `PATCH /configs` | 2 | `mode` only; every other field is accepted and ignored |
| `PUT /configs` | -- | 405. Config reload is the file watcher's job |
| `GET /proxies`, `GET /proxies/{name}` | 1 | |
| `PUT /proxies/{name}` | 2 | select a member |
| `DELETE /proxies/{name}` | 2 | clear a selection back to the configured default |
| `GET /proxies/{name}/delay` | 3 | |
| `GET /group`, `GET /group/{name}` | 1 | groups only; same shape as `/proxies` |
| `GET /group/{name}/delay` | 3 | |
| `GET /rules` | 1 | |
| `GET /connections` | 1 | WebSocket or one-shot; `?interval=` |
| `DELETE /connections`, `DELETE /connections/{id}` | 1 | |
| `/providers/proxies`, `/providers/rules` | -- | 404. Shoes has rule sets but no provider lifecycle |
| `/cache`, `/dns`, `/storage`, `/restart`, `/upgrade`, `/debug` | -- | 404 |
| `/ui` | -- | 404. Serving a dashboard's static files is out of scope |

A 404 is the right answer for a route mihomo has and shoes does not:
dashboards treat it as "feature absent" and hide the panel. A 500 or a
malformed body would make them retry.

## The endpoint table

What each slice-1 endpoint reads, and the source in shoes it reads from.

| Endpoint | Source |
|---|---|
| `/version` | `env!("CARGO_PKG_VERSION")` |
| `/traffic` | The sum over `outbound_stats::snapshot_all()`, differenced per tick. See [Traffic and memory](#traffic-and-memory) for why not the TUN-edge globals |

## Configuration

One new top-level document kind in shoes YAML, discriminated on its own key
like `client_group`, `rule_group` and `dns_group` are
(`src/config/types/groups.rs:198`):

```yaml
clash_api:
  listen: 127.0.0.1:9090
  secret: change-me                 # required unless listen is loopback
  allow_origins: []                 # CORS; empty means "*"
  max_tracked_connections: 4096
  state_file: /var/lib/shoes/clash-api.json   # slice 2; selections
```

`Config::ClashApi(ClashApiConfig)` joins the enum. Validation refuses more
than one such block across the loaded files, refuses a non-loopback `listen`
with no secret, and refuses an empty secret string. `--dry-run` validates it
like everything else.

`GET /configs` returns the subset of mihomo's `configs` schema that
dashboards read and shoes can answer truthfully:

```json
{
  "port": 0, "socks-port": 1080, "mixed-port": 0, "redir-port": 0, "tproxy-port": 0,
  "allow-lan": true, "bind-address": "*",
  "mode": "rule", "log-level": "info", "ipv6": true,
  "tun": {"enable": false}
}
```

The port fields come from the configured servers: the first `socks`
listener's port, the first `http` listener's port, the first `mixed`
listener's port, zero when none. `tun.enable` is whether a `TunServer` is
configured. `log-level` is `log::max_level()`. Nothing else in mihomo's
schema is reported, and `PATCH` of anything but `mode` is accepted and
ignored so a dashboard that writes `log-level` does not see an error.

## Authentication, binding and CORS

**Bearer secret.** Every request must carry `Authorization: Bearer <secret>`
when a secret is configured. A WebSocket request may carry it as `?token=`
instead, because browsers cannot set headers on a WebSocket handshake and
that is what every dashboard sends. Comparison is constant time. A failure
is `401 {"message":"Unauthorized"}`.

**Binding.** Loopback without a secret is allowed: on a single-user VPS a
dashboard tunnelled over SSH is the common case. Anything else refuses to
start at validation, with a message naming the field. This is the rule
sing-box documents; it is enforced rather than documented here because a
router dashboard reached over the LAN is exactly the case where an open
controller lets any device on the network close connections and, from slice
2, redirect traffic.

**CORS.** Dashboards are web pages served from somewhere else. Every response
carries `Access-Control-Allow-Origin` -- `*`, or the request's origin when it
is in `allow_origins` -- plus `Access-Control-Allow-Headers: Authorization,
Content-Type` and `Access-Control-Allow-Methods: GET, POST, PUT, PATCH,
DELETE, OPTIONS`. `OPTIONS` on any path answers `204` with those headers and
no auth check, which is what preflight requires. A secret-less loopback
listener with `*` is reachable by any page the user visits, through
`http://127.0.0.1:9090`; that is the same exposure mihomo has, and the
mitigation is the secret. The security notes say so.

**TLS** is not served. mihomo offers it behind a separate option and almost
no deployment uses it; a LAN dashboard that needs it puts a reverse proxy in
front, as it would for mihomo.

## Transport

hyper 1.x, HTTP/1.1 only, one connection per task, served from the same
runtime as the proxies. No router crate: the path space is a dozen fixed
prefixes, matched by hand on `(method, path segments)`.

**WebSocket.** Four endpoints stream, and every dashboard opens them as
WebSockets. The frames are server-to-client text only; the client sends
nothing after the handshake but a close or a ping. That is small enough to
do by hand, and shoes already has both halves: the server-side handshake
computing `Sec-WebSocket-Accept` in `src/websocket/websocket_handler.rs:104`
and frame encoding in `src/websocket/websocket_stream.rs`. The API module
reuses the accept-key computation and the text-frame writer; it answers ping
with pong and treats close as unsubscribe. No `tokio-tungstenite`.

hyper's `on_upgrade` hands back the raw stream after the 101; the stream
loop then runs on it until the client closes or the server shuts down.

**Streaming without WebSocket.** mihomo also serves `/traffic`, `/memory`,
`/logs` and `/connections` as chunked JSON lines to a plain `GET`, and some
CLI tools use that. Both are served from the same producer: a
`tokio::sync::watch` or `broadcast` per stream, one task per subscriber.

**Shutdown.** The listener task takes a `oneshot::Receiver<()>`. Dropping the
sender ends the accept loop and every subscriber task; open WebSockets get a
close frame.

## What the engine must gain

Everything in this section is under `control-connections` unless stated.
The engine changes are the substance of slice 1; the HTTP module is a
renderer over them.

### The connection table

A process-global registry, the same shape as the outbound registry in
`src/outbound_stats.rs`: a `parking_lot::Mutex<HashMap<u64, Arc<ConnectionEntry>>>`
plus an `AtomicU64` id counter. A `ConnectionEntry` is:

```rust
pub struct ConnectionEntry {
    pub id: u64,
    pub network: Network,                 // Tcp | Udp
    pub inbound: &'static str,            // "Socks5", "HTTP", "Tun", "Shadowsocks", ...
    pub source: SocketAddr,
    pub destination: NetLocation,         // host or IP, plus port
    pub sniffed_host: Option<String>,
    pub chain: Arc<str>,                  // the exit outbound's stats key
    pub rule: Option<usize>,              // index into the selector's rule list
    pub started: SystemTime,
    pub upload: AtomicU64,
    pub download: AtomicU64,
    close: tokio::sync::Notify,
}
```

**Registration** returns a `TrackedConnection` guard holding the `Arc` and
removing the entry from the map on drop. The guard lives in the forwarding
task's stack frame, so a connection aborted by a reload -- `main.rs` aborts
the server tasks -- or by a panic still leaves the table. There is no path
where an entry outlives its task.

**Counting** attaches where counting already attaches. `OutboundCountingStream`
(`src/outbound_counting_stream.rs`) counts into an `Arc<OutboundCounters>`
today; it gains an `Option<Arc<ConnectionEntry>>` and increments both on the
same code path. One wrapper, two targets, no second wrapper on the hot path.
The message-stream twin does the same for UDP.

**Closing.** `DELETE /connections/{id}` calls `entry.close.notify_one()`. The
forward loop selects between the copy and `close.notified()`; on close it
shuts down both halves the way the copy's own completion does. The entry is
removed when the guard drops, not when close is requested, so a dashboard
that deletes and immediately re-lists sees the connection until it is
actually gone rather than a lie.

**The cap.** Beyond `max_tracked_connections` live entries, a new connection
is served but not tracked; the registration returns a guard that holds no
entry, and a process-wide `untracked` counter increments. The cap is on
memory, not on service, and it is reported in `/connections` as an
`"untracked": N` sibling of `connections` so the omission is visible.
Closed connections are not retained; mihomo does not retain them either.

### Where connections are registered

Both forward paths, because a router runs a TUN and a VPS runs listeners:

- **Listener path.** `forward_tcp` in `src/tcp/tcp_forward.rs:35`, after
  `setup_client_tcp_stream` returns, when the exit outbound is known. The
  UDP paths in `process_stream` (`src/tcp/tcp_server.rs:199`) register one
  entry per bidirectional association in `run_udp_copy`, and one entry per
  destination session inside `UdpRouter` for the two per-destination shapes.
- **TUN path.** `handle_tcp_connection` in `src/tun/mod.rs:417`, at the same
  point. UDP flows through `udp_manager.rs` register per flow.

### Source address

`process_stream` does not receive the peer address; the accept loop at
`src/tcp/tcp_server.rs:81` has it and uses it only for the closing log line.
It is threaded through `process_stream`, `ForwardRequest` and the UDP entry
points as a `SocketAddr`. The TUN path has the source from the packet. Unix
socket listeners report `0.0.0.0:0`.

### Inbound type

`ServerProxyConfig` already implements `Display`
(`src/config/types/server.rs:831`); the inbound name is its display form
mapped onto mihomo's spelling where one exists (`Socks5`, `HTTP`, `Mixed`,
`Shadowsocks`, `Trojan`, `Vmess`, `Vless`, `Hysteria2`, `Tuic`, `Tun`).
Captured once per listener, not per connection.

### Exit outbound and rule index

Two pieces of information exist at connect time and are dropped:

- `ClientProxySelector::judge` computes a `rule_index` and returns only the
  decision (`src/client_proxy_selector.rs:331`). `ConnectDecision::Allow`
  gains `rule_index: usize`. The cached path stores the index already, so
  the cache needs nothing.
- The chain selects an exit member and wraps the stream in its counters
  (`src/client_proxy_chain.rs:504`), and `OutboundCounters` does not know
  its own key. It gains one: `key: Arc<str>`, set by `outbound_stats::install`,
  one allocation per configured outbound. `TcpClientSetupResult` gains
  `#[cfg(feature = "control-stats")] exit: Arc<OutboundCounters>`, and the
  registration reads `exit.key`. `chains` in the JSON is `[exit_key]`, or
  `[exit_key, group_name]` when the rule's chain group came from a named
  `client_group` -- the group name is on the `ConnectRule` after the change
  in [The proxy model](#the-proxy-model).

Both changes are under `control-stats`, since they are what the stats
feature was always short of; the connection table merely consumes them.

### The group registry

`ValidatedConfigs.outbounds` (`src/config/validate.rs:46`) is an `OutboundSet`
of leaf keys; group membership is resolved away by the time chains are built.
`ValidatedConfigs` gains `groups: OutboundGroupSet`, name to ordered member
list, where a member is a leaf key or another group's name. Installed beside
the outbounds by `launch_servers` (`src/main.rs:667`), replaced on reload.
`ConnectRule` gains `group_name: Option<Arc<str>>` so a connection can report
the group it was routed through.

This is under `control-stats`, not `control-connections`: it is a few hundred
bytes per configured group, in the same class as the counters, and the
desktop daemon's `Stats` message could carry it later.

### Server-mode traffic

`control::stats::StatsSnapshot.upload_bytes` and `download_bytes` keep their
TUN-edge meaning; the FFI and the daemon's `Stats` message document them and
mobile hosts display them. The Clash API does not read them. `/traffic` and
`/connections` totals are the sum over `outbound_stats::snapshot_all()`, which
is populated in every mode. The two disagree by the sniffed prefix and by
bytes a connection wrote before failing, which is the explainable difference
the stats module already documents.

## The proxy model

Dashboards render `GET /proxies` as a map from name to proxy object and
expect certain shapes:

```json
{"proxies": {
  "GLOBAL":   {"name":"GLOBAL","type":"Selector","now":"eu-1","all":["eu-1","eu-2","direct"],"history":[],"udp":true},
  "eu":       {"name":"eu","type":"LoadBalance","now":"","all":["eu-1","eu-2"],"history":[],"udp":true},
  "eu-1":     {"name":"eu-1","type":"Vless","history":[],"udp":true,"alive":true},
  "direct":   {"name":"direct","type":"Direct","history":[],"udp":true,"alive":true}
}}
```

**Leaves** are the outbound registry's keys -- a configured `name`, or the
address, or `direct` (`ClientConfig::stats_key`, `src/config/types/client.rs:585`).
`type` maps `ClientProxyConfig` onto mihomo's names: `Direct`, `Http`,
`Socks5`, `Shadowsocks`, `Snell`, `Vless`, `Trojan`, `Vmess`, `AnyTLS`,
`WireGuard`; `Reality` reports `Vless` since that is what it carries;
`ShadowTls`, `PortForward` and `Naiveproxy` report their own capitalised
names, which dashboards display as text and never switch on. `udp` is
`supports_udp()`. `alive` is `true` until slice 3 measures something;
dashboards grey out `alive: false`, and a lie in the pessimistic direction
would hide working servers. `history` is empty until slice 3. The type
string also needs the protocol on the registry entry, so `OutboundSet`
carries it beside the address.

**Groups** are the group registry's entries with `type: "LoadBalance"`,
which is what a round-robin group is in Clash terms, and `now: ""`, because
there is no chosen member. In slice 2 a `select` group reports `Selector`
and its choice.

**`GLOBAL`** is synthetic. Every dashboard assumes it exists and uses it as
the picker in Global mode. In slice 1 it lists every leaf, reports
`Selector` with `now` set to the first leaf, and `PUT` on it is 405 until
slice 2 gives it meaning.

`GET /group` is the same map filtered to groups; `GET /proxies/{name}` and
`GET /group/{name}` are one entry or 404.

## Rules

`GET /rules` returns `{"rules":[{"type":"DomainSuffix","payload":"example.com","proxy":"eu"}]}`,
one per `ConnectRule` in the order the selector holds them -- which is the
order that matters, since `rule_index` indexes into it.

Shoes rules are not Clash rules: one `ConnectRule` carries a list of masks
and a list of rule sets, any of which matches. The rendering picks, per rule,
one `type` and one `payload`: a rule with a single mask renders as that mask
(`Domain`, `DomainSuffix`, `IPCIDR`, `IPCIDR6`, `Match` for the any-mask),
using `NetLocationMask`'s `Display`; a rule with several, or with rule sets,
renders as `type: "RuleSet"` with a payload naming the sets and the mask
count. `proxy` is the group name when the rule routes through a named
group, otherwise the exit key of its only chain, `REJECT` for a block.

The rendering of the mask list is the only place this design summarises
rather than reports. A connection's `rule` and `rulePayload` fields use the
same rendering for the rule at `rule_index`, so what a dashboard shows next
to a connection is what it shows in the rule list.

## Traffic and memory

**`/traffic`** ticks once a second. Each tick sums the outbound registry,
subtracts the previous sum, and sends `{"up":Δ,"down":Δ}`. The first frame
is zero. One producer, one `watch` channel, any number of subscribers; a
subscriber that cannot keep up drops ticks rather than buffering them.

**`/memory`** ticks once a second with `{"inuse":rss,"oslimit":0}`. `inuse`
is the resident set size from the OS: `/proc/self/statm` on Linux, which is
the router and the VPS; `mach_task_basic_info` on macOS for development;
zero elsewhere. Not jemalloc's own counters: the library does not choose the
allocator, only `main.rs` does (`src/main.rs:81`), and a figure that means
something on the CLI and nothing in a library host is worse than an OS
figure that means the same everywhere.

## Logs

`BroadcastLogWriter` (`src/control/logs.rs:31`) is a `LogWriter` already;
what is missing is the CLI installing one. Logging initialises before the
config loads (`src/main.rs:214`), so whether an API is configured is not yet
known when the writer list is fixed. The pattern for that exists: 
`DynamicFileLogWriter` (`src/logging.rs:191`) writes into a slot filled
later. A `DynamicBroadcastWriter` does the same, installed unconditionally
under `clash-api` and costing one pointer until the API starts, at which
point it allocates a 512-line ring. A build with the feature and no
`clash_api:` block pays nothing measurable.

`/logs` sends `{"type":"info","payload":"<target>: <message>"}` per line,
filtered by `?level=` (`debug`, `info`, `warning`, `error`, `silent`; the
default is `info`). The backlog is sent first, then live lines. A slow
subscriber is disconnected rather than buffered without bound, which is what
the `broadcast` receiver's lag error gives for free.

## Reload

The file watcher aborts every server task and starts new ones
(`src/main.rs:476`). The API listener is not a server task: it is started
once after the first successful prepare and lives until shutdown, so a
dashboard's WebSockets survive a reload.

What it reads is what reload replaces. The outbound and group registries are
reinstalled by `launch_servers`; the connection table drains as the old tasks
abort and their guards drop; the rule list a connection's `rule_index` points
into is the one on the selector that judged it, held by `Arc`, so an old
connection's rule renders correctly against the old list even after a new
one is installed. `/rules` reports the current list.

The `clash_api` block itself can change. After a reload, `main.rs` compares
the new block to the running one: same `listen` and `secret` and the
listener stays; anything else stops it and starts a new one, on the new
address, with a log line. A reload that removes the block stops the
listener.

## Slice 2: selection and mode

**Config.** `ClientConfigGroup` gains two fields:

```yaml
client_group: eu
mode: select                # round_robin (default) | select
default: eu-1               # required when mode is select
client_proxies: [eu-1, eu-2]
```

Validation refuses `select` on a group with a chain member that is itself a
pool, because "the selected member" must be one outbound. A `select` group
reports `type: "Selector"` and `now`.

**Runtime.** `ClientChainGroup` gains `selected: AtomicUsize` consulted
instead of the round-robin index when the group is `select`. `PUT
/proxies/{group}` with `{"name":"eu-2"}` looks the group up by name in the
group registry, which from slice 2 holds an `Arc<ClientChainGroup>` beside
the member list, and stores the index. Connections already open keep their
chain; new ones take the selection. `DELETE /proxies/{group}` restores
`default`.

**Persistence.** `state_file` holds `{"selections":{"eu":"eu-2"},"mode":"rule"}`,
written through a temporary file and a rename as `AppliedState::save` does
in the daemon, and read at launch and after every reload. A selection naming
a member the new config no longer has is dropped with a warning. The file's
location is the config's responsibility, because a router's writable
filesystem is not where the config lives.

**Mode.** `PATCH /configs {"mode":"global"}` sets a process-wide
`AtomicU8`. `ClientProxySelector::judge` consults it first: `rule` is
today's behaviour; `direct` routes everything through the `direct` outbound;
`global` routes everything through `GLOBAL`'s selection. `GLOBAL` therefore
needs a chain per leaf, which `launch_servers` builds at install from the
validated configs via `chain_builder` -- one `ClientChainGroup` per leaf,
held by the group registry. A connection routed by mode reports
`rule: "Global"` or `rule: "Direct"` and no `rule_index`.

## Slice 3: latency

`GET /proxies/{name}/delay?url=...&timeout=...` opens an HTTP GET to `url`
through the named leaf's chain, measures time to the first response byte,
and answers `{"delay":ms}` or `{"message":"Timeout"}` with 504. The result is
appended to a per-leaf ring of ten `{"time","delay"}` entries reported as
`history`, and `alive` becomes "the last measurement succeeded". `GET
/group/{name}/delay` runs the members concurrently and answers a map.

A `urltest` group mode that picks by measured delay is the natural next step
and is not designed here.

## Error mapping

| Condition | Status | Body |
|---|---|---|
| Missing or wrong secret | 401 | `{"message":"Unauthorized"}` |
| Unknown route | 404 | `{"message":"Not Found"}` |
| Unknown proxy, group, connection id | 404 | `{"message":"<kind> not found"}` |
| Method not supported on a known route | 405 | `{"message":"Method Not Allowed"}` |
| Unparseable JSON body, bad `?level=`, bad `?timeout=` | 400 | `{"message":"<reason>"}` |
| `PUT /proxies/{name}` on a non-select group (slice 2) | 400 | `{"message":"not a selector"}` |
| Delay test timed out (slice 3) | 504 | `{"message":"Timeout"}` |

Every body is JSON with a `message`, which is what dashboards display.

## RSS budget

The scenario includes routers, where the RSS discipline MOBILE.md wrote down
for phones applies again with a different ceiling. The per-connection entry
is the only per-connection cost this design adds:

| Field | Bytes |
|---|---|
| id, network, inbound pointer, rule index, started | 40 |
| source | 32 |
| destination, host form worst case | 24 + hostname |
| sniffed host, when present | 24 + hostname |
| chain (`Arc<str>`, shared) | 8 |
| two counters | 16 |
| `Notify` | 24 |
| `Arc` header and map slot | 48 |

About 220 bytes with IP destinations, about 300 with typical hostnames. At the
default cap of 4096 tracked connections that is 1.2 MB worst case, which is
the number the cap exists to bound. The plan measures this rather than
trusting the table: the figure that matters is the delta in resident size at
the cap with and without the feature.

The log ring at 512 lines of about 120 bytes is 60 KB, allocated only once a
listener starts. The group registry and the key on each `OutboundCounters`
are per-configured-item, not per-connection.

## Security notes

- **A controller is a control plane.** From slice 1 it closes connections;
  from slice 2 it redirects every connection on the machine. The secret is
  the whole of the access control, which is why a non-loopback bind refuses
  to start without one and why the comparison is constant time.
- **Loopback without a secret is reachable from a browser.** Any page the
  user visits can `fetch("http://127.0.0.1:9090/connections")` and, with the
  CORS wildcard, read the answer. mihomo has the same property. The
  documentation for the block says to set a secret anyway; the design does
  not force it on loopback because SSH-tunnelled dashboards are the common
  server case and the user of that machine already has root.
- **The connection table is a record of who talked to what.** It is in
  memory only, never written, and it is gone when the process exits. The
  `/logs` stream carries whatever the log level carries; at `debug` that
  includes destinations. Neither is new exposure beyond what the log file
  already holds, but the API makes it readable over the network, and the
  secret is what gates it.
- **`/memory` and `/version` leak nothing** a `ps` on the same host would
  not.
- **No request body is trusted.** Bodies are bounded at 64 KB and parsed
  with serde; a field this design does not use is ignored, never echoed.

## Testing

The lesson from the daemon work: a unit test of a helper says nothing about
whether the caller calls it. Every claim in this spec that the code must
honour gets a test at the level where the claim is visible.

**Wire level, through a real listener on `127.0.0.1:0`:**

- Auth: no header is 401, wrong secret is 401, right secret is 200,
  `?token=` works on a WebSocket path and is ignored on a plain path.
- CORS: `OPTIONS` answers 204 with the headers and no auth; a GET carries
  `Access-Control-Allow-Origin`; an origin outside `allow_origins` is
  refused.
- Shape: `/`, `/version`, `/configs`, `/proxies`, `/group`, `/rules`,
  `/connections` each deserialise into structs written from mihomo's
  schema, so a renamed key fails the build of the test rather than a
  dashboard in production.
- Unknown routes and methods map per the error table.

**Through a forwarded connection:** a SOCKS inbound and a direct outbound on
loopback; a client connects, sends asymmetric byte counts in each direction,
and the test asserts the entry appears with the right source, destination,
inbound, chain, rule index and counts, that `DELETE /connections/{id}`
ends the client's stream, and that the entry is gone afterwards. Then the
same with the connection ended by the client, asserting the guard removed
it. Then with the cap set to one and two connections, asserting the second
is served and `untracked` is 1.

**The server-mode traffic claim:** the same forwarded connection, no TUN,
asserting the `/traffic` tick after the transfer is non-zero in both
directions. This is the test that fails on today's code.

**Reload:** start with one config, open a WebSocket, rewrite the config,
assert the socket is still open and `/proxies` reflects the new file.

**Mobile isolation:** `cargo build --features control-stats --lib` and
`--features ffi,control-stats,network-extension`, then `nm` on the artifact
asserting no symbol from `clash_api` or `connection_table`. Run in CI on the
existing mobile jobs, since those are the builds the claim is about.

**Defect sweep**, as before: with the registration call at `forward_tcp`
removed, with the `rule_index` never set, with the `Notify` never selected
on, and with the traffic tick reading the TUN globals, at least one test
above must fail. Recorded in the plan.

## Order of work

1. Feature flags, `ClashApiConfig`, discriminator, validation rules, the
   bind-without-secret refusal. Tests at the config level.
2. Engine: `rule_index` on the decision, `key` on the counters, `exit` on
   the setup result, `groups` on `ValidatedConfigs`, source address through
   `process_stream`. Under `control-stats`. Tests that the values arrive at
   `forward_tcp`.
3. The connection table and guard, the second counting target, registration

   `control-connections`. The forwarded-connection tests.
4. The HTTP module: listener, auth, CORS, routing, the one-shot endpoints.
   Wire-level tests.
5. Streams: WebSocket upgrade reusing the handshake code, `/traffic`,

7. Mobile isolation check in CI. RSS measurement at the cap.
8. A live run against yacd and metacubexd pointed at a shoes on a VPS, with

## Decisions

| Question | Decision | Why |
|---|---|---|
| Config format | Shoes' own; no Clash YAML | User's call. Dashboards do not need it; launchers do, and they are out of scope |
| Host | The CLI; `shoesd` later, unchanged contract now | The scenario is server, VPS, router |
| HTTP stack | hyper 1.x, hand-matched routes, hand-rolled WebSocket | Already in the graph; the frames are one-way text; the handshake code exists |
| Traffic source | Outbound registry sum, not the TUN globals | The globals are zero in server mode |
| Memory figure | OS RSS | Means the same thing regardless of allocator or host |
| Connection ids | Monotonic `u64`, decimal string | Dashboards treat ids as opaque; a counter cannot collide across a reload |
| Closed connections | Not retained | mihomo does not; a router has no memory for a history |
| Cap behaviour | Serve, do not track, count the omission | A limit on memory must not be a limit on service |
| `GLOBAL` in slice 1 | Synthetic `Selector`, `PUT` is 405 | Dashboards assume it; refusing the write honestly beats a fake success |
| `alive` before slice 3 | `true` | The pessimistic lie hides working servers |
| Rule rendering | One type and payload per shoes rule | Shoes rules are lists; Clash rules are not; a summary is stated as one |
| Persistence location | Explicit `state_file` | A router's config directory is often read-only |
| Selection persistence format | JSON via temp-and-rename | Same reasoning as the daemon's applied-state record |
| TLS | Not served | Same as mihomo's default; a reverse proxy is the answer |

## Deliberately out of scope

- **Clash config import** and `PUT /configs`. A translator project, if ever.
- **Providers**, proxy or rule. Shoes' rule sets are files on a watcher;
  there is no update lifecycle to expose.
- **`/dns`, `/cache`, `/storage`, `/restart`, `/upgrade`, `/debug`.**
- **`/ui`.** Static hosting of a dashboard is a reverse proxy's job.
- **`urltest` groups.** Named as the step after slice 3.
- **Per-connection process name** (`processPath`). Needs a socket-to-pid
  lookup that is platform work; the field is sent empty.
- **TLS on the listener.**
- **Exposing the connection table over the daemon's gRPC.** The registry is
  designed so `WatchConnections` could be added; it is not added here.
- **Fixing the TUN-edge globals in server mode.** They keep their documented
  meaning; the API reads a different source.
