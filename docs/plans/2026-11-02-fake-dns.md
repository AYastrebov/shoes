# Fake DNS beyond the TUN, and a sharper Fake IP: implementation plan

**Goal:** Give non-TUN inbounds (SOCKS, HTTP, mixed, tproxy) the fake-IP
treatment the TUN already has, sharing one pool where inbounds serve the same
clients, and close the gaps in the TUN's own Fake IP that leak hostname
routing or cost needless traffic.

**Why not port upstream's:** upstream cfal/shoes's Fake DNS (#195 and later)
sits on an ingress refactor we do not have (`IngressTarget`,
`PreparedDestination`, `tcp/ingress.rs`, `routing/ingress.rs`), a resolver
trait that exchanges raw DNS wire bytes, its hickory fork's public `Message`
fields, a WireGuard server inbound, and a persistence layer with file locks.
Porting it means porting all of that. Our `src/dns/fake_ip/` (pool,
responder, bypass) is sound and tested; this plan grows it, taking upstream's
semantics where they are better and saying so.

**Spec of record:** upstream's `docs/src/content/docs/dns/fake.md` for
behaviour we copy; this file for what we do differently.

**Status (2026-11-02):** Phase 2 landed in #152, reshaped by
`docs/specs/2026-11-02-fake-dns-convergence.md`, which supersedes the
sketch below where they differ: restoration happens once, in the rule
judge (`ClientProxySelector::judge`), not on `ForwardRequest` or per UDP
datagram; the router restores once per session and drops or ends on an
unmapped address; the TUN's `fake_ip` key is an alias moved onto its
`dns:` block. Phases 1, 3 and 4 are that spec's deliveries B, C and D,
recorded in `ROADMAP.md`.

## Decisions (2026-11-02)

- Order: Phase 2 (Fake DNS on non-TUN inbounds) first, then Phase 1, then
  Phases 3 and 4; all four are in scope.
- `https_records` defaults to `suppress`, unlike upstream's `forward`:
  hostname routing holding matters more than ECH and the HTTP/3 hint.

## Global constraints

- The mobile TUN path keeps working unchanged unless a phase says otherwise,
  and every change to it is behind config or proven by a TUN test.
- clippy `-D warnings` in every configuration, including
  `--target aarch64-apple-ios` and `cargo ndk -t arm64-v8a`.
- Each new test is watched failing first (defect planted back).
- No Cyrillic. Commit subjects `area: imperative summary`.

## Phase 1: TUN Fake IP refinements (one PR)

Mobile-facing; no new plumbing.

1. **HTTPS/SVCB records.** Forwarded today with their real `ipv4hint` /
   `ipv6hint` / ECH, so a browser can connect to a hint address and skip the
   hostname route. Add `https_records: forward | suppress` (upstream's names).
   `suppress` answers HTTPS and SVCB with an empty NOERROR.
2. **IPv6 range.** Add an optional `ipv6_network` (a ULA range, e.g.
   `fd00:fa1e::/64`); AAAA is synthesised from it when set, NODATA as today
   when not. Pool keyed by (name, family); the TUN restore path already takes
   `IpAddr`. Reject v6 ranges inside `::ffff:0:0/96`; restore v4-mapped
   addresses through `to_canonical()`.
3. **TTL.** Make it configurable (`ttl_secs`), default unchanged at 1. The
   10-minute reuse guard already protects a mapping an app still uses; a
   higher TTL cuts query volume but outlives a restart (there is no
   persistence), when cached answers get the reset/drop.
4. **Range validation.** Refuse a fake network (either family) that overlaps
   the TUN's own address/netmask, a literal client-proxy address, a DNS
   upstream or bootstrap literal, or a rule `override_address`. Today nothing
   checks, and an overlap silently black-holes that endpoint.
5. **Small fixes.** The validation error still says DNS "arrives over UDP"
   (TCP/53 is handled now); responder decisions are not counted (add answered
   / forwarded / bypassed counters next to `UNMAPPED_REFUSED`).

Tests: responder tests per new option; pool tests for the v6 family and
v4-mapped restore; validation tests per overlap kind; a TUN-level test that a
suppressed HTTPS query is answered locally.

## Phase 2: Fake DNS on non-TUN inbounds (one or two PRs)

Desktop/shoesd-facing.

1. **Config and ownership.** `fake_ip` on a listener's `dns:` block and on a
   `dns_group`, same options as the TUN's. Pools move into `DnsRegistry`
   (`dns/builder.rs`): one per named group (inbounds naming the group share
   it), one private pool per inline block. The TUN keeps its `fake_ip:` key
   and gets its pool from the registry too, so a TUN and a SOCKS listener can
   share one by naming the same group.
2. **TCP restore.** Landed in `ClientProxySelector::judge` (see the
   status note): a mapped fake address becomes `Address::Hostname`; an
   unmapped in-range one is blocked, and `forward_tcp` refuses it before
   sniffing or answering DNS (fail closed, as the TUN does).
3. **UDP restore.** In `routing/udp_router.rs`, once per session as it is
   made, not per datagram. Two fixes come with it, both already made in
   the TUN: `connect_future` must not resolve a restored hostname locally
   before judging (a leak), and replies must keep the fake address as their
   source, not the resolved real one.
4. **Port-53 interception.** A SOCKS/HTTP/tproxy destination on port 53 is
   answered by the responder: UDP inside the router (reply written back with
   the original destination as source), TCP through `tun/dns_tcp.rs`'s
   handler moved to `dns/fake_ip/` and shared. Forwarded queries go where the
   client sent them, through the rules, as in the TUN.

Tests: restore and fail-closed through a SOCKS listener (TCP and UDP), a
SOCKS UDP query to port 53 answered with a fake address and the follow-up
connection routed by name, reply source is the fake address, shared pool
between two listeners naming one group.

## Phase 3 (optional): forward through the `dns:` resolver

Forwarded and bypassed queries currently go to the resolver the client
addressed. Upstream sends them through the configured `dns.servers` instead,
via a raw-message exchange on the resolver trait. That needs a wire-level
`exchange` on our `Resolver` (hickory can send raw messages), plus a guard
that rejects real answers or SVCB hints inside a fake range. Worth it if a
configured DoH/DoT should carry all DNS; otherwise skip.

## Phase 4 (optional): persistence

`state_file` keeping mappings across restarts, so a raised TTL survives one.
Upstream's version (atomic writes, lock file, reservation blocks, checkpoint
every 60 s) is substantial; only worth it if Phase 1's TTL is raised in
practice.

## Out of scope

WireGuard server inbound (we have none), `global_settings.default_dns`, a
standalone DNS listener.
